To handle [On-demand Revalidation](https://nextjs.org/docs/basic-features/data-fetching/incremental-static-regeneration#using-on-demand-revalidation), we use `Revalidator` plugins.

A `Revalidator` plugin revalidates one or more Next.js sites when a Drupal entity is **inserted**, **updated** or **deleted**.

Out of the box, the `next` module ships with two revalidators:

- The [`Path`](https://github.com/chapter-three/next-drupal/blob/main/modules/next/src/Plugin/Next/Revalidator/Path.php) revalidator revalidates a Next.js site based on the entity path.
- The [`Cache Tag`](https://github.com/chapter-three/next-drupal/blob/main/modules/next/src/Plugin/Next/Revalidator/CacheTag.php) revalidator revalidates a Next.js site based on [cache tags](https://nextjs.org/docs/app/building-your-application/data-fetching/incremental-static-regeneration#using-cache-tags).

Select the revalidator for each entity type at `/admin/config/services/next/entity-types`.

---

## Path Revalidator

The `Path` revalidator sends the entity's path to the Next.js revalidate URL as a `path` query parameter, e.g. `?path=/blog/my-article`.

### Changing an alias

When an alias changes, Drupal no longer knows the old path — an entity only exposes its current URL. To keep the previous path working, install the [Redirect](https://www.drupal.org/project/redirect) module: it stores the old path and creates a redirect from it. Redirect entities are revalidated on their **source** path, so the old URL is purged from the Next.js cache and starts serving the redirect.

Without the Redirect module, the old path can not be revalidated automatically — there is nothing left in Drupal pointing at it.

### Trailing slashes

If your Next.js site uses `trailingSlash: true`, normalize the path in your revalidate route handler before calling `revalidate`:

```ts title=pages/api/revalidate.ts
// Add the trailing slash expected by trailingSlash: true.
const path = (req.query.slug as string).replace(/\/?$/, "/")

await res.revalidate(path)
```

## Cache Tag Revalidator

The `Cache Tag` revalidator sends the entity's Drupal cache tags to the Next.js revalidate URL. Combine it with the `tags` option on the frontend so list pages and pages referencing other entities are revalidated automatically.

On the Drupal side, configure for example the `node.article` entity type with the `Cache Tag` revalidator. It sends:

- The entity tag, e.g. `node:42`, when **Revalidate entity cache tag** is checked.
- The list tags, e.g. `node_list` and `node_list:article`, when **Revalidate entity list cache tags** is checked.
- Any **Additional cache tags** you configured (one per line).

On the Next.js side, tag your queries accordingly.

Revalidate a **list page** whenever an article is created, updated or deleted:

```tsx title=app/page.tsx
const articles = await drupal.getResourceCollection<DrupalNode[]>(
  "node--article",
  {
    params: {
      "filter[status]": 1,
      "fields[node--article]": "title,path",
    },
    next: {
      tags: ["node_list:article"],
    },
  }
)
```

Revalidate a **detail page** whenever the article itself changes:

```tsx title=app/blog/[slug]/page.tsx
const node = await drupal.getResource<DrupalNode>("node--article", uuid, {
  next: {
    tags: [`node:${nodeInternalId}`],
  },
})
```

### Invalidating pages when a referenced entity changes

Drupal cache tags cascade to referenced entities in render arrays, but a JSON:API response fetched by Next.js does not carry them. To invalidate a page when one of its referenced entities (a media, a taxonomy term…) changes, tag the page with the referenced entity's cache tags. Build them from the `included` relationships:

```tsx title=app/blog/[slug]/page.tsx
const node = await drupal.getResource<DrupalNode>("node--article", uuid, {
  params: {
    include: "field_image,field_tags",
  },
})

// Collect cache tags of the node and every included (referenced) entity.
const referenced: DrupalMedia[] | DrupalTaxonomyTerm[] =
  (node.included as any[]) ?? []
const tags = [
  `node:${internalId}`,
  ...referenced.map((item) => `${item.type}:${item.drupal_internal__id}`),
]

// Re-fetch with tags (second pass) or wrap the initial fetch with tags
// derived from the translated path.
```

With this pattern, editing a media in Drupal sends `media:123` through the `Cache Tag` revalidator and every page tagged `media:123` is revalidated — no custom invalidation code needed.

### Multilingual sites

The revalidate URL also receives a `locale` query parameter containing the entity language (e.g. `&locale=fr`), so multilingual frontends can revalidate only the localized page variants that use it.

## Custom Revalidator

You can implement your own revalidator plugin using the Drupal Plugin API.

```php title=custom_module/src/Plugin/Next/Revalidator/CustomRevalidator.php
<?php

namespace Drupal\custom_module\Plugin\Next\Revalidator;

use Drupal\next\Event\EntityActionEvent;
use Drupal\next\Plugin\RevalidatorBase;

/**
 * Provides a custom revalidator.
 *
 * @Revalidator(
 *  id = "custom",
 *  label = "Custom Revalidator",
 *  description = "Description for the custom revalidator"
 * )
 */
class CustomRevalidator extends RevalidatorBase {

  /**
   * {@inheritdoc}
   */
  public function revalidate(EntityActionEvent $event): bool {
	// Get the entity.
    $entity = $event->getEntity();

    // Get the sites configured for this entity.
    $sites = $event->getSites();

    // Get the action: insert, updated or delete.
    $action = $event->getAction();
  }

}
```

Visit the configuration page of an entity type at `/admin/config/services/next/entity-types`.

You should see **Custom Revalidator** available as a plugin under On-demand Revalidation. Select it and save.

Now, whenever an entity is inserted, updated or deleted, the `CustomRevalidator::revalidate` function will be called.

<Callout>

**Note:** `revalidate` is called on [shutdown](https://api.drupal.org/api/drupal/core%21includes%21bootstrap.inc/function/drupal_register_shutdown_function/9.3.x). This means `dump()` calls will not be registered. Use a breakpoint instead.

</Callout>

## Configurable Revalidator

To implement a configurable `Revalidator` plugin, extend the `ConfigurableRevalidatorBase`.

```php title=custom_module/src/Plugin/Next/Revalidator/ConfigurableRevalidator.php
<?php

namespace Drupal\custom_module\Plugin\Next\Revalidator;

use Drupal\Core\Form\FormStateInterface;
use Drupal\next\Event\EntityActionEvent;
use Drupal\next\Plugin\ConfigurableRevalidatorBase;

/**
 * Provides a configuratble revalidator.
 *
 * @Revalidator(
 *  id = "configurable_revalidator",
 *  label = "Configurable Revalidator",
 *  description = "Description for the configurable revalidator"
 * )
 */
class ConfigurableRevalidator extends ConfigurableRevalidatorBase {

  /**
   * {@inheritdoc}
   */
  public function defaultConfiguration() {
    return [
      'message' => NULL,
    ];
  }

  /**
   * {@inheritdoc}
   */
  public function buildConfigurationForm(array $form, FormStateInterface $form_state) {
    $form['message'] = [
      '#type' => 'textfield',
      '#title' => $this->t('Message'),
      '#default_value' => $this->configuration['message'],
    ];

    return $form;
  }

  /**
   * {@inheritdoc}
   */
  public function submitConfigurationForm(array &$form, FormStateInterface $form_state) {
    $this->configuration['message'] = $form_state->getValue('message');
  }


  /**
   * {@inheritdoc}
   */
  public function revalidate(EntityActionEvent $event): bool {
    // Get the configuration.
    $message = $this->configuration['message'];
  }

}
```

You should also provide the schema definition at `web/modules/custom/custom_module/config/custom_module.schema.yml`:

```yml
next.revalidator.configuration.configurable_revalidator:
  type: mapping
  mapping:
    message:
      type: string
      label: "Message"
```
